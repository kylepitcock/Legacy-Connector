### Round 2 notes

- **`super.` calls of facade-served members** are now generic for 1.4.7, 1.5.2 and 1.6.4: `ShimLinker` sends an `invokespecial` of a legacy method the shim lacks to the facade's `mcc$super$<name>` (the default body; a plain facade method may dispatch back to the override, so it is never used for a super call). Hooks that exist in 1.7.10 under another shape are bridge rows instead (`forward/1.5.2/bridge-methods.tsv`: `Block.isLadder`, `isBlockSolidOnSide` -> `isSideSolid`, `canCreatureSpawn`), which also makes a mod's override of them effective. Test: `SuperFacadeLinkTest`.
- **Texture sheet API**: `Texture` and `Rect2i` are real classes (RGBA pixel buffer, `copyFrom`, `fillRect`, GL id through the texture manager's handle table); `TextureStitched.init` keeps the sheet and frame list and positions the sprite. The host stitches the atlas, so nothing calls a sprite's `init`/`loadTexture`: a mod sprite class that loads its own pixels there does not get to (open: map the custom-loader hook `load(IResourceManager, ResourceLocation)` onto it, `TextureAtlasSprite.hasCustomLoader`).
- **Downloaded skins and capes** go through the existing `ThreadDownloadImageData` (skins.minecraft.net URLs are answered with the profile's texture); `cloakUrl`/`skinUrl` of a player are those URLs. `updateCloak()` is a no-op (the cape is the native player's).
- Open and deliberately not done: LWJGL `Cursor`/`Mouse.setNativeCursor` (held branch), `GameData`/`ItemData` (FML's item id persistence in level.dat: ids are not saved that way here), the NEI classes (held branch `worktree-agent-acbdb94d99cd8c4b2`), the FML network handshake classes (`FMLNetworkHandler`, `NetworkModHandler`), the `GameSettings` key binding index API (`keyBindings` is empty here), `Item.encode/getBlockId/getMetaData` (classes of the mods themselves).
