# 1.2.5: what the shim worker (B) needs from the loader worker (A)

Written 2026-11-16 by the run-time worker after the first server runs of real 1.2.5 jars (`-Pmappings125`, `./gradlew runServerSubTest -PsubTestDir=run-sub125`).

## 1. Name unjoined members after Feather, not after the obfuscated letter

`Notch125To147.UNJOINED_PREFIX + name` gives `mcc125$b` for a method whose obfuscated name is `b`. The client and the server of 1.2.5 are obfuscated separately, so `Block.b(World,int,int,int,EntityPlayer)` on the client is another
letter on the server: a shim hook keyed by the letter serves one side only. The join table already has the Feather name of every 1.2.5 member (`Block.use`, `Item.useOn`, `BlockWithBlockEntity.createBlockEntity`,
`Slot.onItemRemoved`, ...). Please emit `mcc125$<feather name>` (add the arity or the descriptor hash when two overloads share a name). The shim worker then writes the adapters once:

- calls: rows of `forward/1.4.7/member-manual.tsv` (`R ... static ... Redirects125`), done for the members of section A of the link probe that are calls (font, chat, explosion, tooltip, ...), keyed by the **client letters today**
  (`mcc125$b` of `FontRenderer`, `mcc125$l` of `Minecraft`, ...): they have to be re-keyed when the names change; the list is in `Redirects125` and the tail of `member-manual.tsv`;
- overrides (the larger part, and the one that decides whether a content mod works): the game calls the 1.3+ shape of a method and never the 1.2.5 override a mod declares. Shim hooks needed, each a default method that
  the matching 1.7.10-shaped method calls when the mod class overrides it (`Block.getHardness(int)` is the first, done): `Block.use` (1.2.5 `onBlockActivated(world, x, y, z, player)`), `Item.useOn`
  (`onItemUse(stack, player, world, x, y, z, side)`), `BlockWithBlockEntity.createBlockEntity` (no-argument `getBlockEntity()`), `Block.onRemoved`, `Block.updateMetadataOnPlaced`, `Block.addCollisions`
  (`getCollidingBoundingBoxes`), `Slot.onItemRemoved`, `Container.onClickSlot` (shift flag), `PlayerEntity.pickUp`.

## 3. From the run-time worker, round 2 (2026-11-16)

- **Return-type mismatches of overridden hooks are invisible to the JVM**: the 1.2.5 server `BaseMod.onTickInGame(MinecraftServer)` is `void`, the shim's is `boolean` (the client one is `boolean` in both). A `void` override is a different method, so the shim's calls never reach it. Handled in the shim for this one hook by reflection
  (`ModLoaderHooks125.callServerTick`); a generic fix is a bridge in `OverrideBridges` for "same name and parameters, other return kind" (void against boolean/int), refused today ("the result kind changed").
- **`forge/ArmorProperties.ApplyArmor(EntityLiving, ItemStack[], DamageSource, double)` returns `int` in Forge 3.3**; the shim's class extends the shared 1.7.10 `ArmorProperties` whose static returns `float`, so a call with the `...)I` descriptor does not link (no mod in the corpus calls it, only the Forge jars).
- **`forge/IMinecartCollisionHandler` and `EntityMinecart.setCollisionHandler(IMinecartCollisionHandler)`**: the shim's `forge.IMinecartCollisionHandler` extends the 1.7.10 interface, but a mod's call `EntityMinecart.setCollisionHandler(forge/IMinecartCollisionHandler)` has the `forge/` type in its descriptor and the shim method takes the 1.7.10 type: it needs a descriptor row (Railcraft, 2 units).
- **The loader does NOT produce the `mcc125$<name>` override names the shim hooks expect (checked 2026-11-16 with `checkLegacyMod -Pmappings125 -PkeepDir` on `ElementalCreepers_v2.3_sp_MC1.2.5` and `EE2ClientV1.4.6.7`, `javap` of the translated classes).**
  `EC_EntityFriendlyCreeper.a(EntityAnimal)EntityAnimal` (the U row `bc a (Lbc;)Lbc; makeChild`) stays `a`, not `mcc125$makeChild`; the shim hooks `EntityAnimal.mcc125$makeChild` and `Block.mcc125$updateMetadataOnPlaced` therefore never match yet. In `ee.BlockEETorch` the 1.2.5 `c(World,IIII)V` (the corpus report lists it as `updateMetadataOnPlaced`) comes out as **`onBlockDestroyedByPlayer`** (its body schedules a block update and reads the metadata, it is a placement hook): a wrong rename, the mod's placement code would run when the block is destroyed. Please rename overrides of U-row members to `mcc125$<Feather name>` (with the parameter types in 1.4.7 names) and check why `c` joined to `onBlockDestroyedByPlayer` there.
- The Forge handler interfaces now use `EntityLivingBase` where Forge 3.x says `EntityLiving` (the 1.4.7/1.5.2 chain renames every `EntityLiving` of a mod's signatures to `EntityLivingBase`; an interface with the old type is never implemented by the mod). If the loader stops doing that for 1.2.5 jars, `forge/ISpecialArmor` and `forge/ISpecialMobSpawnHandler` need the old type back.

## 4. From the run-time worker, task 1 (missing game classes), 2026-11-16

Measured on the real corpus with the real names (Calamus + Feather 1.2.5 client/server, Feather 1.4.7, Mojang 1.2.5 jars read with `javap`; a class counts only when a class that is NOT a copy of a
game class names it, the side taken from the jar name). **Of the classes in the round 3 list only three are named by retained mod code**; every other reference sits in a patched game class that the loader drops
(`LegacyChunkCache`, `LoadWorldChunkPacket`, `AddItemPacket`, `WorldSaveConflictScreen`, `MultiplayerWorld$BlockReset`, `SaplingItem`, `LogItem` and the server `CommandHandler`: the Forge, ModLoader(MP), NEWTON
and Mystcraft game-class patches and nothing else), so they need no alias and no shim class. The three, and a defect class behind the list:

- **BossEntity** (`ajn` client, `xb` server; Feather names `doTakeDamage(DamageSource,int)` = `e`, `takeDamage(EnderDragonPart,DamageSource,int)` = `a`, field `maxHealth` = `aA`): IC2 1.103 `EntityMiningLaser` (client and server;
  reads `EnderDragonPart.dragon.getHealth()` for an achievement) and Twilight Forest's `EntityTFHydra` (client and server; extends it, overrides `getMaxHealth()` and `takeDamage`, calls `doTakeDamage`). The shim now has the class,
  with real behaviour read from the 1.2.5 bytecode: `legacyconnector/v1_6_4/net/minecraft/src/EntityDragonBase` (extends `EntityLiving`, implements `IEntityMultiPart` so `new EntityDragonPart(this, ...)` works; members named exactly
  like Feather's: `maxHealth`, `takeDamage`, `doTakeDamage`). **Request**: a class row `BossEntity -> net/minecraft/src/EntityDragonBase` the way `MODLOADER_MP` is handled (not a 1.4.7 notch name), with the members of the class
  looked up by their Feather names in that class and the inherited ones (`getHealth` ...) through the 1.2.5 superclass (`LivingEntity`, which joins). `EnderDragonPart` (`dg`, intermediary `C_2608212`) already has a 1.4.7 class under the
  same intermediary id; its field `dragon` is typed `BossEntity` in 1.2.5 and `IEntityMultiPart` in the shim (field `entityDragonObj`): the descriptor fix applies, but a use of the field's value as `EntityDragonBase`
  (IC2 reads `dragon.getHealth()`) needs a `checkcast` after the `getfield` or the verifier rejects an interface-typed receiver.
- **A class tier by Calamus intermediary id** (the defect class). The join names classes by Feather name, but Feather 1.2.5 and 1.4.7 name some classes differently or put them in another package while the Calamus
  intermediary id is the same (the same class). Computed from the two Feather jars (`C_` id equal, Feather name different, 1.2.5 name absent from 1.4.7):
  client `MultiplayerInteractionManager` -> `ClientPlayerInteractionManager`, `MultiplayerWorld` -> `ClientWorld`, `MultiplayerChunkCache` -> `ClientChunkCache`, `FireballRenderer` -> `ProjectileRenderer`,
  `MapItem` -> `FilledMapItem`, `PaintingItem` -> `DecorationItem`, `RemoveEntityPacket` -> `RemoveEntitiesPacket`, `PortalForcer`/`ScheduledTick` -> `server/world/PortalForcer`/`ScheduledTick`, client `ChunkCache` -> `server/world/chunk/ServerChunkCache`

  miss); server `CommandSource` (`um`; **real use**: Mystcraft's `ChatHandlerTPX`, PortalGun's `mod_PortalGun`, Forge's own `BaseMod` copy; `getSourceName` and `sendMessage(String)` have the same Feather names in 1.4.7) ->
  `server/command/source/CommandSource` (= `ICommandSender`), `PendingCommand`, `MinecraftServerAccess`, `ServerProperties` and the server GUI classes (all under `server/dedicated`). There is no wrong-reuse evidence for classes yet

## Members125 rows (Members125 worker, 2026-11-16)

Shim members added under the `mcc125$<Feather name>` names the loader emits (no table row needed for those). What still needs the loader, with the evidence from probe p3 (289 distinct / 324 stubs after the three batches):

   (1.2.5 `u_()` = createBlockEntity, 4 jars). The adapter is refused (needs a World), so the call should fall back to the U name: the shim has `ItemStack.mcc125$getTooltip` (R row exists in `member-manual.tsv`, `Redirects125.tooltip`),
